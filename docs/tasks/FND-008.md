## Product context

Business OS (REBZZ) is a modular, multi-tenant platform. The shared foundation is
built first, then advanced e-commerce, then clinics, then cafés and restaurants.
Every industry solution must reuse the same foundation.

Before applications, workers, background jobs, payment integrations, or domain
modules exist, the platform needs one consistent configuration approach. Without
it, each package parses raw environment strings on its own, which produces
duplicated parsing, inconsistent defaults, and unsafe credential handling.

## Architecture decisions

Recorded in `docs/adr/0003-validated-environment.md`.

- **Zod 4** is the validation library, as an exact runtime dependency.
- `@business-os/configuration` is the **single source of truth** for every
  supported `BUSINESS_OS_*` variable: one definition each, containing its schema
  and metadata, with no parallel registry and no enum defined twice.
- The **existing package is extended**, not replaced. A second configuration
  package would split one responsibility across two competing sources of truth.
- Environment remains **separate** from Configuration, Feature Flag, Entitlement,
  and Secret. This task implements environment-variable definition and validation
  only. A variable may be classified sensitive without this becoming a secrets
  vault.
- Values are **injected explicitly**. The library never reads `process.env`,
  `Bun.env`, or `.env`, and never mutates global state.
- Validation is **fail-fast**, avoiding permissive coercion.
- Errors are **sanitized by construction**: stable code plus variable name only.
- **Redaction derives from registry metadata**, not a second secret-key list.
- `@business-os/database` **keeps its own boundary validation**. FND-008 creates
  no dependency from the database package to the configuration package, so no
  cyclic workspace dependency exists.
- Bun remains the development **and** production runtime. No Node.js deployment,
  no Node.js CI, no runtime migration.

No architectural conflict was found. Rule 11 already required a typed registry
with `key`, `type`, `default`, `validation`, `visibility`, and
`restart-required`, plus rejection of unknown keys; rule 05 required centralized
secret redaction; rule 13 required stable error codes. All three are satisfied.

The first eight are visible to the runtime parser. The last two are reserved for
local database administration and are never returned by the runtime parser.

Host, port, database name, and the TLS decision are shared by both credential
pairs, so they carry their own parser group. This avoids hard-coding key lists in
the parsers.

## Schema behavior

- **Environments:** `local`, `test`, `staging`, `production` only. Case-sensitive.
  Nothing is ever defaulted to `local` or `production`.
- **Log levels:** `debug`, `info`, `warn`, `error`; defaults to `info` only when
  the variable is absent. An explicitly empty or invalid value fails.
- **Port:** decimal integer string converted to a number. Verified rejections:
  `0`, `-1`, `1.5`, `abc`, `Infinity`, `NaN`, `""`, `"   "`, `70000`, `1e3`.
  `z.coerce.number()` is deliberately avoided because it turns `""` into `0`.
- **Boolean:** only the exact strings `true` and `false`. `TRUE`, `1`, `0`, `yes`,
  and trailing whitespace are rejected. `Boolean("false")` is avoided.
- **Secrets:** empty values and `REPLACE_WITH_*` placeholders are rejected.

## Production TLS policy

`BUSINESS_OS_DB_SSL` is required, never defaulted. A `production` runtime
configuration with `ssl: false` is rejected with
`FORBIDDEN_IN_PRODUCTION` on `BUSINESS_OS_DB_SSL`. Production with `ssl: true` is
accepted. `local` with explicit `ssl: false` is accepted because the local
PostgreSQL service is loopback-bound; the runbook and ADR record that this is a
deliberate local exception, not a default.

## Local administration parser

`parseLocalAdminEnvironment` requires `BUSINESS_OS_ENV` to be present and exactly
`local`; any other runtime is rejected with `FORBIDDEN_IN_PRODUCTION`. It validates
the shared connection settings plus the administrator credentials, returns only
those fields, never falls back to application credentials, and provisions or
modifies nothing.

## Error handling

`EnvironmentConfigError` exposes `code` and `variable` and nothing else.

Codes: `MISSING_REQUIRED_VALUE`, `INVALID_VALUE`, `UNKNOWN_VARIABLE`,
`FORBIDDEN_IN_PRODUCTION`.

- `safeParse` is used; the Zod error is discarded, never returned.
- No unsanitized Zod error is attached as `cause`; `error.cause` is `undefined`.
- Only the first failing variable is reported, to limit what a single probe
  reveals.
- The library writes nothing to stdout or stderr.
- "Missing" versus "invalid" is decided from the registry and the supplied
  source, **not** from Zod internals, because Zod 4 issue codes differ between
  validators (`invalid_value` for enums versus `invalid_type` for strings).

Undeclared `BUSINESS_OS_*` keys are rejected as `UNKNOWN_VARIABLE`. Ordinary OS
variables such as `PATH`, `HOME`, and `LANG` are ignored. Variables registered for
another subsystem stay valid even when a given parser does not consume them.

## Secret classification and redaction

Both database passwords are classified sensitive. No non-secret entry is
misclassified. No sensitive entry is ever marked display-safe. The registry stores
no credential values.

`summaryEnvironmentConfig` displays a value only when its registry entry is
explicitly display-safe, and redacts everything else. Because both credential
pairs map onto the `user` and `password` fields, a value is additionally redacted
when any variable feeding the same field is sensitive, so redaction is correct no
matter which parser produced the object.

Verified summary of a local runtime config:

```
BUSINESS_OS_ENV=local, BUSINESS_OS_LOG_LEVEL=info, BUSINESS_OS_DB_HOST=[redacted],
BUSINESS_OS_DB_PORT=55432, BUSINESS_OS_DB_NAME=[redacted],
BUSINESS_OS_DB_APP_USER=[redacted], BUSINESS_OS_DB_APP_PASSWORD=[redacted],
BUSINESS_OS_DB_SSL=false, BUSINESS_OS_DB_CONFIGURED=true
```

Administrator credentials never appear in a summary.

## Build verification

`packages/configuration/package.json` build was changed to add
`--packages external`, consistent with ADR-0002 and with the database package.

**Reason:** without it the build inlined a complete copy of Zod, producing a
763 KB bundle with zero external imports, which duplicated the library,
contradicted the declared runtime dependency, and diverged from the approach used
by `@business-os/database`. With the change the output is **16.3 KB** with Zod
external and zero inlined Zod source.

Verified absent from the built output: `bun:sql`, any `bun:` specifier, `Bun.`,
`Bun.env`, and `process.env` reads. The shared source contains no Bun globals and
performs no logging.

The runtime configuration's `database` object exposes exactly
`host, port, database, user, password, ssl`, which matches
`DatabaseConfigInput` in the database package. Compatibility was verified
structurally without importing that package.

Four real defects were found by these tests and fixed:

1. The local administration parser validated only the two administration
   variables, so `DB_HOST`, `DB_PORT`, `DB_NAME`, and `DB_SSL` were stripped and
   reading them failed. Fixed by introducing parser groups so each parser is
   assembled from metadata instead of a scope-only list.
2. `has_database`-style field mapping matched on category, so the database name
   (an infrastructure category) was never found and
   `BUSINESS_OS_DB_CONFIGURED` reported `false` for a fully configured database.
   Fixed by matching on the shared `database-connection` group.
3. The summary never emitted `BUSINESS_OS_DB_APP_USER` because user and password
   map to two registry variables, not one. Fixed by considering every variable
   feeding the field and redacting when any of them is sensitive.
4. Missing-versus-invalid detection relied on the Zod issue `input` field, which
   Zod 4 does not emit; the enum issue code is also `invalid_value`, not
   `invalid_enum_value`. Every missing required value was therefore reported as
   `INVALID_VALUE`. Fixed by deriving the distinction from the registry and the
   supplied source instead of from Zod internals.

## Remaining limitations

1. **The local `.env` was intentionally not updated** because the task forbids
   changing it. It therefore still lacks `BUSINESS_OS_ENV`,
   `BUSINESS_OS_LOG_LEVEL`, `BUSINESS_OS_DB_HOST`, and `BUSINESS_OS_DB_SSL`. A
   developer adopting the new parsers must add those keys locally. This does not
   affect the committed template or any test.
2. **Local tooling still uses FND-006 manual parsing.** Migrating
   `packages/database/tools/local/*` to the central registry is explicitly
   deferred to a separately reviewed integration task.
3. **`@business-os/database` is not wired to the environment parsers.** The shapes
   are compatible, but no dependency was created, by design.
4. **The schema type parameter is unused.** `DatabaseClient` in the database
   package remains `Record<string, never>` because no tables exist.
5. **An administrator configuration summarised through the runtime field labels
   reports its values under the runtime variable names.** Every such value is
   redacted, so nothing leaks, but the label is cosmetic rather than exact.
6. **`docs/` remains outside Biome's include list**, so the ADR and this record
   are not format-checked.
7. **This package still builds with `--target bun`**, unlike the database package
   which uses `--target node`. The output is standard ESM and uses no Bun APIs,
   but the targets are inconsistent. Changing the target was not requested.
8. **GitHub Actions was not observable** from this environment.
