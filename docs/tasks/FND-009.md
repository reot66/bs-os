## Product context

Business OS (REBZZ) is a modular, multi-tenant platform. Error handling must work
consistently across shared platform modules, e-commerce, clinic services,
restaurant services, background jobs, external integrations, database operations,
and future API and event systems. Different applications must not invent
incompatible error formats, but domain-specific errors must remain possible
without editing every shared infrastructure package.

## Architecture decisions

Recorded in `docs/adr/0004-shared-error-contracts.md`.

No architectural conflict was found. Rule 05 requires a standard error contract
and a central error-code registry with centralized redaction, and D-054 commits
the platform to a structured, auditable error surface; rule 13 requires stable
error codes and forbids clients parsing error text. Both are satisfied. The
prompt's explicit exclusion of HTTP status codes does not conflict with rule 13,
which does not mandate transport mapping in this layer.

## Runtime decision

Bun remains the development **and** production runtime, plus package manager,
workspace manager, test runner, and bundler. Bun `1.3.14`. No Node.js
deployment, no Node.js CI, no runtime migration.

## Error catalog

Eleven generic platform codes. No industry-specific codes were invented.

| Code | Category | Public message | Retryable |
| --- | --- | --- | --- |
| `VALIDATION_ERROR` | validation | The request is invalid. | no |
| `UNAUTHENTICATED` | authentication | Authentication is required. | no |
| `FORBIDDEN` | authorization | You do not have permission to perform this action. | no |
| `NOT_FOUND` | authorization | The requested resource was not found. | no |
| `CONFLICT` | domain | The operation conflicts with the current state. | no |
| `PRECONDITION_FAILED` | domain | The operation's requirements were not met. | no |
| `BUSINESS_RULE_VIOLATION` | domain | The operation cannot be completed. | no |
| `RATE_LIMITED` | infrastructure | Too many requests. Please try again later. | **yes** |
| `DEPENDENCY_UNAVAILABLE` | infrastructure | The service is temporarily unavailable. | **yes** |
| `OPERATION_TIMEOUT` | infrastructure | The operation timed out. | **yes** |
| `INTERNAL_ERROR` | internal | An unexpected error occurred. | no |

Categories: `validation`, `authentication`, `authorization`, `domain`,
`infrastructure`, `internal`.

The catalog is frozen, every nested entry is frozen, mutation attempts have no
effect, `ErrorCode` is derived from the catalog so an unknown code is a compile
error, and no entry carries an HTTP status or any runtime/environment data.

## Public API

Nine exports: `BusinessOsError`, `ERROR_CATALOG`, `ERROR_CATEGORIES`,
`ERROR_CODES`, `getErrorCatalogEntry`, `isErrorCode`, `isBusinessOsError`,
`normalizeUnknownError`, `toPublicError`. Types: `ErrorCatalogEntry`,

No mutable shared object, no second error class, and no accidental export of
internal diagnostic context.

## Error class behaviour

`BusinessOsError extends Error`. Verified: `instanceof Error` and
`instanceof BusinessOsError` both true; `name` is `BusinessOsError`; a
non-empty stack is produced; the native `message` is the safe public message.
`code`, `category`, `retryable`, and `publicMessage` all come from the catalog.
An unknown code throws `TypeError` rather than guessing a classification.

## Cause handling

`cause` is typed `unknown`, stored as a non-enumerable native cause, and never
eagerly stringified. Verified with an `Error` cause (identity preserved), an
object cause, and the primitives `"a string"`, `42`, `true`, and `null`. The
original cause is never mutated. `cause` is absent entirely when not supplied.

## Normalization

`normalizeUnknownError` preserves the identity of an existing `BusinessOsError`.
Anything else is wrapped as `INTERNAL_ERROR` with the original value kept only
as an internal cause. Tested with: a native `Error`, a string, a number,
`0`, `-1`, booleans, `null`, `undefined`, `NaN`, a `Symbol`, a function, a
`Date`, an array, a plain object, a **cyclic** object, and an object with a
hostile `toString`. Normalization never throws for ordinary values.

Untrusted input is never trusted:

- `{ code: "FORBIDDEN", message: "Fake privileged error" }` becomes
  `INTERNAL_ERROR` with the catalog message. A trusted-looking code is not
  enough.
- An object with a `code` **getter** is normalized without the getter ever being
  invoked.
- An object with a hostile `toString` is normalized without `toString` being
  called.

## Public serialization

`PublicError` is `{ code, message, retryable }` — exactly those three keys, and
frozen (mutating it throws `TypeError`).

`toJSON()` delegates to the approved public shape, so `JSON.stringify(error)`
and `toPublicError(error)` produce identical output for **every** catalog code.
Verified absent from all public output: internal message, original cause,
private context, stack trace, and any sentinel.

## Retryability

Classification is advisory metadata only. Three infrastructure codes are
retryable (`RATE_LIMITED`, `DEPENDENCY_UNAVAILABLE`, `OPERATION_TIMEOUT`) and the
other eight are not. No retry is ever attempted: repeated `toPublicError` calls
produce equal results with no side effects. The ADR and the runbook-level
documentation state that retry safety still depends on idempotency, transaction
state, limits, and caller policy.

## Security design

- **No real credentials anywhere.** Tests use only `TEST_SECRET_DO_NOT_EXPOSE`,
  `TEST_SQL_INTERNAL_DETAIL`, and `TEST_PRIVATE_CONTEXT`.
- **No sensitive cause exposed by JSON serialization** — `cause` is
  non-enumerable and `toJSON` bypasses it.
- **No private context exposed** — `context` is defined non-enumerable and
  non-writable.
- **No stack traces in public results.**
- **No arbitrary object stringification** — no property of an untrusted value is
  read during normalization.
- **No automatic trust of a `code` property** on untrusted input.
- **No global exception handlers** — no `process.on`, no `uncaughtException`,
  no `unhandledRejection`.
- **No automatic retries.**
- **No dependency on database credentials or tenant context**, and no tenant
  authorization logic.
- **No framework-specific code and no HTTP coupling.**
- **No new third-party dependencies.**
- **No accidental cross-package imports** — verified the package imports nothing
  but its own relative modules.

An exhaustive sweep confirmed **no sentinel leaked** through
`JSON.stringify`, `toPublicError`, object spread, `Object.assign`, public
conversion of the cause itself, normalization, nested public conversion, or
arrays of public errors.

## Known limitations

1. **Raw internal errors remain unsafe to log.** The package protects the public
   serialization boundary, not the log stream. A trusted diagnostic system can
   still read the cause, internal message, and private context, and nothing here
   redacts them. The logger's redaction policy is deferred to FND-010.
2. **`context` is stored, not validated or redacted.** It is a debugging aid for
   trusted code only. Passing a secret into it would store that secret in memory.
3. **Two error styles coexist** until a separately approved migration adapts
   `BootstrapConfigError`, `EnvironmentConfigError`, `DatabaseConfigError`, and
   `DatabaseConnectionError`.
4. **`NOT_FOUND` is categorised as `authorization`.** This is deliberate: a
   caller must not be able to distinguish "absent" from "not yours", so the
   decision to disclose belongs to the application boundary. Documented in the
   ADR.
5. **No HTTP mapping, no correlation/request IDs.** A correlation context field
   would be domain- and transport-specific and belongs to the observability
   layer.
6. **Retryability is a boolean only.** It carries no backoff hint or retry-after
   duration, which a transport adapter may need.
7. **`docs/` remains outside Biome's include list**, so the ADR and this record
   are not format-checked.
8. **GitHub Actions was not observable** from this environment.
9. **FND-005-FIX1 caveat still applies**: the root links two workspace packages
   to `node_modules`, which weakens resolution-time isolation for them.
