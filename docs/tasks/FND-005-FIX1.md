## Problem

FND-005 added `@business-os/configuration` and revealed that package-name
imports fail from the repository root, even though both workspace packages
compile successfully.

Verified reproduction at commit `c0ba892` after `bun run build`:

```
$ bun -e 'import { CONTRACTS_PACKAGE_ID } from "@business-os/contracts"; console.log(CONTRACTS_PACKAGE_ID);'
error: Cannot find module '@business-os/contracts' from '/home/commander/Projects/personal/business-os/[eval]'
Bun v1.3.14 (Linux x64)
(exit 1)

$ bun -e 'import { parseBootstrapConfig } from "@business-os/configuration"; console.log(parseBootstrapConfig({ BUSINESS_OS_ENV: "test" }));'
error: Cannot find module '@business-os/configuration' from '/home/commander/Projects/personal/business-os/[eval]'
Bun v1.3.14 (Linux x64)
(exit 1)
```

Both imports failed. Any future application, database package, or
root-level tool would therefore be unable to import the platform foundation
by package name.

## Root cause

Bun's default **isolated** linker only materializes
`node_modules/<scope>/<name>` symlinks for packages that are actually
*depended upon*. Declaring `"workspaces": ["packages/*"]` registers a package in
the workspace graph, but it does **not** create a dependency edge.

The root manifest declared only two devDependencies and did not depend on
either internal package, so no `node_modules/@business-os` scope existed at the
repository root.

Observed installation layout before the fix:

```
$ ls -la node_modules/
drwxr-xr-x  .bin
drwxr-xr-x  @biomejs
drwxr-xr-x  .bun
lrwxrwxrwx  typescript -> .bun/typescript@5.9.3/node_modules/typescript

$ ls node_modules/@business-os
ls: cannot access 'node_modules/@business-os': No such file or directory

$ ls packages/contracts/node_modules packages/configuration/node_modules
ls: cannot access '...': No such file or directory
```

Note the trap this created: `bun pm ls` *did* list both workspace packages
(`@business-os/configuration@workspace:packages/configuration`), which can look
like successful registration, while the actual filesystem link required for
resolution was absent. Registry resolution, not workspace registration, is what
governs import success.

Resolution from *inside* `packages/configuration` worked only because a package
may import itself by its own name via its own `exports` map
(self-reference). That mechanism never applied to the repository root.

## Approved solution

Declare the two internal packages as explicit **workspace development
dependencies** of the root manifest:

```json
"devDependencies": {
  "@biomejs/biome": "2.5.15",
  "@business-os/configuration": "workspace:*",
  "@business-os/contracts": "workspace:*",
  "typescript": "5.9.3"
}
```

Why `devDependencies`: the repository root is a development and orchestration
workspace, not a production business application. This authorizes root-level
development and verification tooling to import the internal packages without
publishing them or creating a production dependency edge.

`workspace:*` guarantees the dependency always resolves to the local workspace
package and can never be satisfied by a same-named registry package.

Future application packages must independently declare their own
`workspace:*` dependencies. This root declaration does not replace that
requirement.

Explicitly **not** used, per the approved solution: no hoisted linker, no
`bunfig.toml`, no `bun link`, no manual symlinks, no TypeScript path aliases,
no registry wildcards, and no change to existing package `exports`.

### Regression prevention

`tests/workspace-resolution.test.mjs` imports exclusively through the published
package entry points by package name:

```js
import { CONTRACTS_PACKAGE_ID } from "@business-os/contracts";
import { RUNTIME_ENVIRONMENTS, parseBootstrapConfig } from "@business-os/configuration";
```

It does **not** import `../packages/contracts/src/index.ts` or
`../packages/configuration/src/index.ts`. Resolution is therefore genuinely
exercised: if a future change removes a root dependency entry, switches the
linker, breaks the workspace graph, or breaks a package `exports` map, these
three tests fail. They also assert runtime behavior, not merely that resolution
succeeds, so a regression to a wrong default log level or wrong environment
parsing is caught too.

CI discovery is automatic: the workflow's `bun run test` step invokes the root
script, which runs `bun test` from the repository root and discovers the new
file. **No CI workflow change was made or required.**

Biome coverage was extended with `"tests/**"` so the new file is actually
linted and format-checked rather than silently skipped. The checked-file count
rose from 11 to 12, which confirms the file is genuinely covered.

### Measured limitation: resolution-time isolation for these two packages

This must be stated plainly rather than glossed over.

Because the root now owns `node_modules/@business-os/*` symlinks, Node/Bun's
upward directory walk lets **any** nested package resolve these two names
without declaring them. Measured directly, before and after the fix:

| Check | Before fix (`c0ba892`) | After fix |
| --- | --- | --- |
| root -> `@business-os/contracts` | exit 1 | exit 0 |
| `packages/configuration` -> `@business-os/contracts` (undeclared) | **exit 1 (blocked)** | **exit 0 (resolves)** |
| `packages/contracts` -> `@business-os/configuration` (undeclared) | **exit 1 (blocked)** | **exit 0 (resolves)** |
| `packages/configuration` -> own name (self-reference) | exit 0 | exit 0 |

The pre-fix baseline was confirmed on a throwaway copy of `c0ba892` extracted
with `git archive` into `/tmp/opencode`, so the comparison is measured rather
than assumed; that scratch copy was deleted afterward and never touched the
working repository.

Interpretation: the approved fix resolves the reported bug and does not
weaken third-party dependency isolation, but it **does** mean that for these two
internal packages, cross-package access is now governed by convention rather
than by resolution failure. Declaring a dependency is still required by
convention and by review, but an omitted declaration is no longer automatically
caught by the resolver.

This is inherent to the approved approach. Every alternative the task
explicitly forbids (`bunfig.toml`, hoisted linker, `bun link`, manual
symlinks, path aliases) either does not solve the root import or is a prohibited
substitute, so the trade-off is inherent to the approved solution, not to this
implementation. It is recorded here so the reviewer can weigh it.

No automated enforcement of import boundaries exists in the repository today,
neither before nor after this change.

## Known limitations

1. **Future consuming packages must declare their own `workspace:*`
   dependencies.** Root-level `devDependencies` authorize imports only from the
   root. They do not satisfy the requirement for `apps/*` or any future
   `packages/*` member, which must declare what it imports.
2. **Resolution-time isolation no longer blocks undeclared internal imports**
   for `@business-os/contracts` and `@business-os/configuration`, as measured
   in the table above. Declaration discipline is now enforced by review, not by
   the resolver.
3. **No automated import-boundary enforcement** exists. Nothing currently fails
   a build when a package imports a package it did not declare.
4. **Root workspace dependency edges make the root a consumer** of both
   internal packages. This is intentional for a development/orchestration root,
   but it means the root can no longer be treated as dependency-free.
5. **A future package that needs a third instance of the same dependency at a
   different version** will still hit isolated-layout constraints. This task
   does not address version conflicts.
6. **`bun audit` covers known advisories only**, not license review or
   dependency ownership.
7. **Markdown and YAML remain unlinted**; this record is outside the Biome
   include list by design.
8. **GitHub Actions remains unobserved** from this environment.
9. FND-002, FND-003, FND-004, FND-005, and this task all still await
   independent review.
