## Product context

Business OS (REBZZ) is a modular, multi-tenant platform. Phase 1 is the shared
platform foundation, later phases are advanced e-commerce, doctors and clinics,
and cafés and restaurants. All industry systems must reuse the same foundation
without duplicating the business core or the database infrastructure.

FND-007 establishes the shared database access layer. It implements **no**
business entity and no industry functionality, and it deliberately creates **no**
schema.

## Runtime decision

Bun is the development **and** production runtime, plus package manager,
workspace manager, test runner, and bundler. Bun `1.3.14`. No Node.js
deployment, no Node.js CI, and no runtime migration is authorized or planned.

Shared database code uses standard TypeScript and standard JavaScript APIs only,
with no Bun-specific globals. The package is built as Node-compatible ESM
(`--target node --format esm --packages external`) as a portability measure. That
build setting does not change the production runtime and does not make migration
effortless.

## Drizzle ORM decision

- Drizzle ORM is the ORM, imported through `drizzle-orm/node-postgres`.
- `pg` is the PostgreSQL driver and pool provider.
- No Prisma, TypeORM, Sequelize, MikroORM, `bun:sql`, custom ORM, or custom
  query builder.
- No large wrapper was created; native Drizzle APIs are used.
- Connections are created explicitly through a factory, so domain services
  depend on a defined boundary rather than on connection internals.
- Migrations are **not** introduced. `drizzle-kit` is not installed.

Recorded in `docs/adr/0002-runtime-portability-and-drizzle.md`.

## Security design

- Configuration is passed explicitly. The shared package never reads
  `process.env`, `Bun.env`, or `.env`.
- No connection is opened at module import time; no global singleton exists; the
  caller owns the lifecycle.
- Validation errors identify the offending key and code but **never** the
  rejected value, so a password cannot leak through an error or log line.
- TLS is explicit and mandatory in configuration; certificate validation is
  never globally disabled. Local tools pass `ssl: false` because they connect to
  loopback only.
- Raw driver errors are never surfaced. `DatabaseConnectionError` keeps only the
  non-sensitive SQLSTATE code.
- Passwords never appear in connection URLs or logs. No logging occurs in the
  shared package at all.
- Role creation never places the password in a JavaScript SQL string.
- The runtime role cannot create tables, schemas, databases, or roles.

Independently re-verified outside the tooling: `false false false false true`.

Memberships: none. Database ownership: none.

Effective privileges (`has_database_privilege` / `has_schema_privilege`, which
account for inheritance):

- database `CONNECT`: true
- database `CREATE`: **false**
- schema `public` `USAGE`: true
- schema `public` `CREATE`: **false**

Observed ACLs:

```
business_os_local database ACL: ...business_os_app=c/business_os_local   (c = CONNECT only)
public schema ACL:              ...business_os_app=U/pg_database_owner   (U = USAGE only)
```

The role does not own the database and inherits no administrative role. The
cluster's `public` schema default already withholds CREATE from PUBLIC
(`=U/` only), which is why no revocation from unrelated roles was necessary or
performed. The stored password is a `SCRAM-SHA-256$` verifier, not plaintext.

No privileges on any future business table are granted; none exist.

## Connection factory behavior

`createDatabase(config)` builds a bounded `pg` `Pool` (default max 10, explicit
connection and idle timeouts) and wraps it with `drizzle({ client: pool })`.
It returns `{ db, pool, ping, close }`.

Verified behavior:

- Creating a handle opens **no** connection (`totalCount`, `idleCount`,
  `waitingCount` all 0 immediately after creation).
- `ping()` performs a real parameterized `SELECT 1` round trip.
- `close()` calls `pool.end()` once; repeated and concurrent `close()` calls
  resolve without error and leave `pool.ended === true`.
- Invalid configuration throws `DatabaseConfigError` **before** any pool is
  created, so no live pool is produced.
- Two handles are fully independent; closing one does not close the other.
- Failures surface as `DatabaseConnectionError` with SQLSTATE only.

## PostgreSQL integration results

Provisioning (`bun run packages/database/tools/local/provision-role.ts`), run
from the repository root, exit 0:

```
Local PostgreSQL 18.6 (Debian 18.6-1.pgdg12+2) on 127.0.0.1
Creating restricted role business_os_app...
Verifying role attributes...
Verifying effective privileges...
  denied CREATE TABLE (SQLSTATE 42501)
  denied CREATE SCHEMA (SQLSTATE 42501)
  application role authenticated and executed a query
Role business_os_app is provisioned and verified.
```

Run twice more afterwards, both exit 0 and both taking the "already exists"
path, proving idempotency and that the password is **not** reset on re-run.

Safe password handling: the password is passed as a query parameter into
`set_config(..., true)`, a transaction-local setting. A **constant** PL/pgSQL
block reads that setting and builds the DDL with `format(..., %I)` for the role
name and `%L` for the password, so PostgreSQL quotes it server-side. The
password never appears in a JavaScript SQL string, and the whole transaction
rolls back if any step fails.

Two defects were found and fixed during provisioning:

1. `has_database_privilege($1, 'CONNECT')` is the two-argument overload, where the
   first argument is a **database** name, not a role name. It failed with
   `database "business_os_app" does not exist`. Corrected to the three-argument
   overload with `current_database()`.
2. The negative DDL checks were initially executed on the **administrator**
   connection, which trivially permitted `CREATE TABLE` and reported a false
   least-privilege violation. They now run on a dedicated **application-role**
   connection, which is the only meaningful way to test the restriction.

## Known limitations

1. **No schema exists.** There are no tables, no migrations, and no
   `drizzle-kit`. `public` is empty and the only user-visible schema.
2. **No migration role.** Schema changes are impossible today by design. A
   separate approved task must add a migration account and Drizzle Kit.
3. **Drizzle's schema type parameter is `Record<string, never>`.** Once tables
   exist, the type must be supplied. The current parameterization is honest for a
   schema-less package.
4. **`pg-cloudflare` is installed transitively** as an optional dependency of
   `pg`. It is unused on this platform and unused in the built output.
5. **`@types/node` is pulled transitively** by `@types/pg`. It is type-only and
   never shipped at runtime.
6. **Portability is designed, not proven.** The build is Node-targeted ESM and
   the package uses no Bun APIs, but no Node.js execution test is a gate in
   FND-007. Switching runtimes would still require evaluation and testing.
7. **The `ping()` check is connectivity only.** It does not validate business
   permissions, and it does not replace authorization tests.
8. **Local tools trust the working directory.** They read `.env` from the
   repository root via Bun's loader, so they must be run from the root. The
   shared package has no such dependency.
9. **Local dev role only.** `business_os_app` has no table privileges because no
   tables exist; its privilege set will need review when schema is introduced.
10. **`docs/` is outside Biome's include list**, so the ADR, this record, and the
    runbook are not format-checked.
11. **GitHub Actions was not observable** from this environment.
12. **Resolution-time isolation note carried from FND-005-FIX1:** `@business-os/database`
    was deliberately **not** added to root dependencies, per the task. Root-level
    code cannot import it by name, and local tools resolve `pg` from within the
    package scope. The FND-005-FIX1 caveat that root-level workspace links weaken
    isolation still applies to the two packages already linked at the root.
