## Baseline migration

- File: `packages/database/migrations/core/0000_baseline_core_schema.sql`
- SQL: `CREATE SCHEMA IF NOT EXISTS core;`
- Generated with `drizzle-kit generate --custom --name baseline_core_schema`,
  which is the supported custom-SQL mechanism for a change that ordinary
  schema generation cannot represent (a schema with no tables).
- Journal entry produced by the generator. No journal entry was hand-written.
- Idempotent: `IF NOT EXISTS` makes it a structural no-op when the privileged
  provisioning already created the schema.
- Contains **no** tenant, user, role, organization, commerce, clinic,
  restaurant, payment, appointment, or customer table, and no seed data.

## Migration parser

`parseLocalMigrationEnvironment(source)` in
`packages/configuration/src/environment.ts`.

- Accepts an explicitly supplied object; never reads `process.env` or `.env`.
- Requires `BUSINESS_OS_ENV=local`; every other runtime is rejected with
  `FORBIDDEN_IN_PRODUCTION` before a connection is attempted.
- Requires migrator credentials; placeholder and empty passwords rejected.
- Validates the shared connection settings through the registry schemas.
- Returns a deeply frozen `{ environment, database }`.
- Rejects undeclared `BUSINESS_OS_*` variables using the existing registry rule.
- Never returns application or administrator credentials.
- `parseRuntimeEnvironment`, `parseLocalAdminEnvironment`, and
  `parseBootstrapConfig` keep their existing output shapes. The local-only
  guard was factored into one shared helper used by both local parsers, with
  no behavioural change.
- Only the CLI entry points read ambient environment and pass it in.

`.env.example` gained matching placeholder entries. The template drift test
passes because it compares the committed template against the registry.

## Migration runner

`packages/database/tools/migrations/apply-local.ts`.

- Explicit `--apply` confirmation; an absent or unrecognized flag refuses.
- Refuses any environment other than `local`, any host other than
  `127.0.0.1`, any database other than `business_os_local`, and a TLS-enabled
  local target.
- Refuses application, administrator, and superuser credentials, and any role
  with inherited memberships.
- Refuses any PostgreSQL major version other than 18.6.
- Never runs at startup, connection creation, package import, or `bun install`.
- Reports SQLSTATE only; passwords, connection strings, and raw driver
  messages are never printed. Configuration errors are reported with their own
  sanitized message rather than mislabelled as a SQLSTATE.
- Releases the lock and the connection in `finally`; no retry loop wraps DDL.
- Does not automatically reverse anything.

## Connection ownership and locking

A single pinned `pg.PoolClient` is checked out, the advisory lock is taken on
that client, and the Drizzle migrator is constructed over **that same client**
(`drizzle({ client })`). A session-level advisory lock is invisible to other
sessions, so locking one pooled connection and migrating through others would
provide no protection.

- Key: `pg_try_advisory_lock(16979, 1)` — two 32-bit integers, deliberately
  avoiding the JavaScript exact-integer range a 64-bit key would exceed.
  `16979` is `'BS'` in ASCII; `1` is the Core migration set.
- Bounded wait: 30 attempts, 1s apart (~30s), then a clear failure. No
  unbounded retry.
- Release in `finally`; releasing the connection ends the session, which
  releases the lock even if the explicit unlock fails.

## Status command

`packages/database/tools/migrations/status-local.ts`.

Reports target database, host, connected role, PostgreSQL version, journal
location, version match, role permission verdict, migration files on disk,
journal existence, applied count, pending count, latest applied timestamp,
journal problems, and an explicit statement that it does not compare the live
schema.

Verified read-only: against a provisioned-but-unmigrated database it reports
`Journal state: UNINITIALIZED`, and the relation count before and after is
identical and zero. It creates no schema, table, journal, or lock.

It reuses the runner's shared helpers, so the two cannot drift apart.

## Journal integrity

Guaranteed and tested:

- Every successfully applied migration is recorded.
- Pending migrations are identified using the migrator's own rule.
- Re-running records nothing and duplicates no row (verified: 1 row before
  and after).
- Missing migration files are detected.
- Modified migration files are detected by SHA-256 comparison — verified for
  real by tampering with the baseline file and confirming the runner refuses.
- Duplicate journal rows are detected.
- The runner fails closed on any finding; nothing is auto-repaired.

## Drift-detection boundaries

Verified: migration-history consistency and migration-file integrity.

**Not** verified: that the live database schema matches the migrations. No
schema-introspection comparison exists. The status command prints this
limitation on every run, and ADR-0006 and the runbook state it explicitly.

## Failure recovery

Tested for real: a deliberately invalid migration was generated through the
supported generator and applied.

- Exit code nonzero.
- The failed migration was **not** recorded (journal count unchanged).
- The partial DDL was rolled back — the probe table did not exist afterwards.
- The advisory lock was released, verified through `pg_locks`.
- No password appeared in the output.
- The committed migration set was restored exactly in a `finally` block.

Drizzle runs pending migrations in one transaction, so a failure rolls back the
batch. No down migrations exist and none are promised; an application rollback
does not restore a schema.

## Concurrency

## Known limitations

1. **`bun audit` exits 1.** `esbuild@0.18.20`, pulled only through
   `drizzle-kit`'s dev-time `@esbuild-kit/esm-loader`, is flagged by
   GHSA-67mh-4wv8-2f99 (dev-server request exposure). It is a devDependency
   path and is not in any production bundle, but the gate does not pass as
   written. A root-level `overrides` entry pinning `esbuild` to `0.25.12` was
   tested: it clears the audit and `drizzle-kit generate` still works, but it
   requires modifying the protected root `package.json`. See Plan amendments.
2. **The migrator holds database-level `CREATE`** and can create extra
   schemas, because Drizzle's migrator requires it. Documented in ADR-0006.
3. **No live schema-drift detection.** Only history and file integrity are
   verified. Stated in the tool output, the ADR, and the runbook.
4. **A gap in the middle of the history is not reported as pending**, because
   the migrator itself would not run it. Such a gap surfaces only as a hash
   mismatch or a missing file.
5. **`drizzle-kit generate` writes unformatted JSON metadata**, so
   `bun run format` must follow generation or the format gate fails. The
   runbook documents this.
6. **Pre-existing type error in a protected file.**
   `packages/database/tools/local/verify-role.ts:302` fails
   `tsc --noEmit` with `TS2722: Cannot invoke an object which is possibly
   'undefined'`. This was confirmed present at the starting commit with no
   FND-011 file involved. Because `tools/local/**` is protected, it was not
   fixed, and `tsconfig.tools.json` is scoped to `tools/migrations/**` so the
   error does not break CI. It should be fixed in a separate authorized task.
7. **Integration tests are opt-in and therefore absent from CI.** Real
   PostgreSQL verification exists but runs only locally, by design of the
   existing CI workflow, which this task must not change.
8. **`0002`-style filename gaps** would appear in a journal if a migration
   were ever deleted; the missing-file check catches that.
9. **The local guard rails refuse remote targets by design**, so this tooling
   cannot be pointed at staging or production as written.
